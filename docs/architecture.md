# RobotCare AI 架构说明

> 文档同时记录目标架构与当前已验证基线。每项状态以 `docs/status_evidence.md` 的运行证据为准。

## 1. 产品边界

【计划】RobotCare AI 是面向普通消费者的独立第三方海尔扫地机器人使用指导与安全故障排查平台。首期深度支持 `JH69U1` 与 `VC35U1`，`P50U1` 仅作为扩展型号。

【计划】系统只允许低风险外部操作：清理外露刷头和传感器窗口、检查充电座或水箱安装、重新配网、正常重启或按已审核说明复位。涉及拆机、电池、电机、电路板、内部零件、冒烟、焦味、异常发热、漏液或带电维修时必须停止排查并建议联系官方售后。

## 2. 目标系统结构

```text
Vue 3 + TypeScript 电脑网页
        │ HTTPS / JSON / JWT
        ▼
FastAPI /api/v1
        ├── 认证与资源所有权校验
        ├── 用户设备与型号服务
        ├── 确定性诊断状态机
        ├── 附件元数据与对象存储适配
        ├── 售后报告生成
        └── 管理员知识与流程维护
        │
        ├──────────────► PostgreSQL（业务数据）
        ├──────────────► pgvector（型号级知识检索）
        └──────────────► 本地目录 / MinIO（图片与报告）
```

- 【已验证】前端已使用 Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus 与 Axios，并通过生产构建。
- 【已验证】后端使用 FastAPI、Pydantic v2、SQLAlchemy 2、JWT、Argon2 与 Alembic；显式初始迁移和 revision 启动门禁已通过 SQLite 测试。
- 【已验证】管理员授权由 FastAPI 依赖在服务器端执行；`AuditLog` 与 Alembic `20260720_0002` 记录型号启停、管理员创建和角色提升等动作。前端路由守卫不作为安全边界。
- 【已验证】数据层已实现 SQLite/PostgreSQL 双方言：SQLite 用 JSON Text 保存 256 维向量并在 Python 中计算余弦相似度；PostgreSQL 使用 `vector(256)` 和数据库内余弦 Top-K SQL。
- 【已验证：实现与静态/单元验证】PostgreSQL 查询保持 HNSW 索引列无 CAST，并在数据库层完成型号过滤、阈值、排序和 LIMIT；迁移定义 `vector` 扩展和 `vector_cosine_ops` HNSW 索引。
- 【待验证】真实 PostgreSQL 尚未运行集成测试；当前不能声称扩展安装、迁移执行、HNSW 可用、查询计划或运行健康已经验证。
- 【已验证】附件开发期使用本地目录，已实现真实图片解码、格式一致性、大小/像素/数量/会话状态限制、随机文件名、所有权隔离和删除失败追踪；切换 MinIO 仍为【计划】。
- 【已验证】诊断反馈分支使用 LangGraph StateGraph；数据库负责会话持久化。LangGraph checkpointer、中断恢复图和模型分类仍为【计划】。

## 3. 核心数据流

### 3.1 分步诊断

1. 【已验证】用户登录并选择归属于自己的设备。
2. 【已验证】用户提交故障描述、可选错误码和图片附件。
3. 【已验证】服务端只选择当前型号 `published` 流程；JSON 目录是唯一种子源，普通用户无法调用 `draft/retired` 流程。管理员已有运营控制台，但在线流程审核与发布仍为【计划】。
4. 【已验证】每次 API 响应只返回一个当前步骤。
5. 【已验证】用户反馈必须携带当前 `step_id`；条件更新保证同一步骤只处理一次，冲突返回 409。“已解决”结束，“未解决”进入下一步。
6. 【已验证】步骤耗尽后会话进入未解决状态并可生成文本与 PDF 报告；危险输入在创建会话前由后端规则阻断。

### 3.2 流程版本与发布

1. 【已验证】流程使用 `stable_key + version` 唯一定位，并区分 `draft/published/retired`。
2. 【已验证】发布或停用版本的内容哈希不可原地改变；修改必须创建新版本。
3. 【已验证】新版本发布时旧发布版本转为停用，已经开始的会话继续引用原 `flow_id` 和原步骤。
4. 【已验证】步骤保存来源 URL、PDF 页码、证据等级、依据摘要和独立的平台策略说明。
5. 【已验证】当前 4 条流程发布、1 条导航流程因证据不足保持草稿。逐步审查见 `docs/flow_evidence_review.md`。

### 3.3 RAG

1. 【已验证】JH69U1、VC35U1 官方 PDF 已登记来源 URL、SHA256、型号和页码，并完成本地解析与目视检查；管理员可查看数量健康，但知识上传/重建/停用和逐条人工审核仍为【计划】。
2. 【已验证】入库按 SHA256 幂等处理；同型号同来源发生变化时，在一个数据库事务内替换旧分片；模拟提交失败的回滚测试证明旧文档和旧分片仍保留。完整版本管理、停用和删除 API 仍为【计划】。
3. 【已验证】SQLite 查询按 `robot_model_id` 过滤并支持 `min_score`；PostgreSQL 查询的型号过滤、阈值、Top-K、排序和无列 CAST SQL 已通过方言编译与单元断言。真实 PostgreSQL 执行仍为【待验证】，默认阈值也尚未经过完整评测校准。
4. 【已验证】检索接口返回内容片段、相关度、来源标题、URL 和页码；113 条评测数据已建立，三项离线规则/目录检查已执行。生成式回答以及型号隔离、检索召回、拒答、分类和忠实度真实链路评测仍为【计划】。
5. 【已验证】状态接口可对比每个型号的文档数、分片数和向量数；当前 SQLite 结果为 JH69U1 `1/31/31`、VC35U1 `1/22/22`。PostgreSQL/pgvector 健康检查脚本已编写，但真实运行仍为【待验证】。

### 3.4 附件与报告

1. 【已验证】附件上传使用 Pillow 校验真实格式和完整解码，同时限制 MIME/扩展名一致、5MB、2500 万像素、每会话 5 张和进行中状态；图片不参与自动视觉诊断。
2. 【已验证】数据库只保存附件元数据和随机存储名，不保存用户本地路径。
3. 【已验证】未解决时报告汇总型号、用户描述、错误码、附件文件名、已执行步骤、步骤来源和第三方免责声明；RAG 检索页码自动汇总仍为【计划】。
4. 【已验证】PDF 使用受权接口幂等生成与下载，文件采用不可预测存储名；脱敏 A4 示例已完成渲染目视检查。Dockerfile 已配置 Noto CJK 字体路径，但 Linux 容器内实际渲染仍为【待验证】。

## 4. 信任与安全

- 【已验证】设备、诊断、附件和报告查询在服务端校验资源所有权；7 个管理员接口统一使用服务器端 `require_admin`，普通用户调用测试均返回 403。
- 【已验证】高风险描述在创建诊断前由后端确定性规则阻断，不依赖 LLM 或前端提示；记录最小化安全事件，不进入普通步骤。
- 【已验证】附件删除先隔离文件并与数据库记录一起变更；物理清理失败时保留可追踪任务，避免静默孤儿文件。
- 【已验证】管理员可读取运营概览、型号、知识健康、安全阻断、未解决报告摘要和审计日志，并可启停型号；型号启停记录操作人、资源与变更前后值。
- 【已验证】型号停用会阻止公共型号发现、新建设备和新开诊断，同时保留历史诊断可读性，避免把运营停用误写成历史数据删除。
- 【计划】知识上传/重建/停用、流程审核发布和评测结果持久化接入相同 RBAC 与审计体系。
- 【计划】日志不得记录密码、JWT、Wi-Fi 密码、完整联系方式或附件内容。
- 【计划】模型输出采用结构化 schema；步骤文本来自已审核数据库记录，而非模型即兴生成。
- 【已验证】官方入口、原始正文和向量状态分开记录；当前两份说明书已入库，但这不代表内容已经完成逐条人工安全审核。
- 【已验证】生产式启动不调用 `create_all()` 修改表结构；数据库必须先升级到 Alembic head。测试可显式启用临时建表。

## 5. 可观测性与交付

- 【已验证】管理员操作已有结构化 `AuditLog`；【计划】请求级 Trace ID、诊断状态变更和报告生成的统一结构化日志。
- 【计划】监控 API 错误率、诊断完成率、拒答率、来源命中率、检索延迟和模型调用成本。
- 【计划】通过单元测试、API 集成测试、权限越权测试、状态机测试、RAG 评测和关键页面端到端测试后，才能在状态文档中标为【已验证】。
- 【已验证：静态契约】Docker Compose、Dockerfile、启动迁移、外部密钥、PostgreSQL/附件/报告持久卷、Noto CJK 字体、服务健康检查和 CI PostgreSQL job 已通过静态配置检查。
- 【待验证：真实运行】当前环境没有 Docker/psql，镜像未构建、Compose 未启动、PostgreSQL 集成测试未运行，GitHub Actions 也尚无远端成功记录。配置存在不能替代运行证据。

## 6. 管理员边界

当前管理员架构是“可审计的运营与安全基线”，不是完整 CMS：

1. 【已验证】后端提供 7 个接口：运营概览、型号列表、型号启停、知识状态、安全阻断、未解决报告摘要和审计日志。
2. 【已验证】安全管理员 CLI 从 `ROBOTCARE_ADMIN_PASSWORD` 环境变量读取新账号密码；创建、提升和幂等重复执行均有测试，密码不进入命令行或审计详情。
3. 【已验证】前端控制台调用真实 API；显示加载/错误状态，并允许启停型号。单元测试与生产构建通过，浏览器 E2E 尚未执行。
4. 【计划】加入知识文档生命周期、流程审核发布和评测执行/结果持久化后，才能称管理员内容运营闭环完成。

## 7. PostgreSQL 与部署验收证据

在真实 PostgreSQL 环境中，至少需要同时获得以下证据，才能把运行状态标为【已验证】：

1. Alembic 升级到当前 head，且 `vector` 扩展存在。
2. `knowledge_chunks.embedding` 的实际类型为 `vector(256)`，余弦 HNSW 索引存在。
3. `tests/test_postgres_integration.py` 通过，证明数据库层 Top-K 和型号隔离；`scripts/postgres_integration_smoke.py` 通过，证明迁移后应用健康、种子型号和持久目录可写。
4. `docker compose build`、`docker compose up -d`、后端/前端健康检查通过。
5. 重建容器后 PostgreSQL 数据、附件和报告仍存在，并保存命令输出或 CI 链接。
